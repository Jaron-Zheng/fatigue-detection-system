# 长时稳定性与性能剖析报告

> 第三轮角色五产出。所有数字来自真实采样（工具：`tools/perf-profile.mjs`，
> CDP `Performance.getMetrics()` + `PerformanceObserver({entryTypes:['longtask']})`），
> 原始数据文件保留在 `docs-evidence/perf-*.json`，可复核。
>
> 执行环境：Windows，Edge 无头（`--headless=new --disable-gpu`），Node v24.19.0
> 执行日期：2026-08-11　服务端口：5180

## 一、长会话内存曲线（演示模式，60 分钟无人值守）

**参数**：`--mode memory --minutes 60`，演示模式（SimulatedDriver 合成剧本），
每 30s 采样一次，共 118 个采样点。
**数据**：`docs-evidence/perf-memory-1786455201119.json`

| 指标 | 数值 |
|---|---|
| JS 堆（首 / 末 / 峰值） | 2.98 MB / 8.19 MB / **10.11 MB** |
| 堆波动区间（全程） | 2.1 – 10.1 MB（GC 锯齿形） |
| DOM 节点数 | 2885 → 稳定在 3900–4700 之间波动 |
| 会话采样条数（终态） | 6930（≤ 容量上限 7200+64，容量控制在生效） |
| 状态机 | 全程 `running`，未死锁、未崩溃 |

采样摘录（完整 118 点见 JSON）：

```text
[0.58min] heap=2.98MB dom=2885   [10.08min] heap=4.75MB dom=4025
[20.09min] heap=5.76MB dom=4153  [30.09min] heap=9.29MB dom=4151
[40.1min] heap=3.96MB dom=3941   [50.1min] heap=7.74MB dom=4348
[56.61min] heap=10.02MB dom=4390 [60.11min] heap=8.19MB dom=4091
```

**结论：无内存泄漏。** 堆大小呈 GC 锯齿形在 2–10MB 区间往复，
后 30 分钟的最低值（如 49.6min 的 3.74MB、52.1min 的 3.94MB）与前 10 分钟同量级，
不存在单调增长趋势；"末值 8.19MB 高于首值 2.98MB"只是采样点恰好落在 GC 前的相位，
峰值全程被 10.11MB 封顶。DOM 节点数与事件/采样容量均受上限约束，
符合设计预期（环形缓冲区与会话数组都有容量上限）。

## 二、主线程长任务与推理帧率

### 2.1 演示模式（无真实推理）

60 分钟内 longtask **仅 1 次，51ms**（约 22.6min 处），累计阻塞 51ms。
合成数据链路的开销可忽略。

### 2.2 真实推理模式（假摄像头，3 分钟）

**参数**：`--mode infer --minutes 3`，`--use-fake-device-for-media-stream`
+ `--use-file-for-fake-video-capture=tools/fixtures/fake-face.y4m`（MediaPipe 官方人像素材），
走完整 `getUserMedia → FaceEngine → 融合` 真实链路。
**数据**：`docs-evidence/perf-infer-1786455536024.json`

| 指标 | 数值 |
|---|---|
| 推理委托 | GPU（WebGL；无头 + `--disable-gpu` 下实为 SwiftShader 软件仿真） |
| 平均推理耗时 `avgInferMs` | **71.7 ms/帧**（首分钟 97.8 → 稳定 71–73） |
| 3 分钟推理帧数 | 1736（≈9.6 fps） |
| longtask 次数 | **1739 次 ≈ 每帧一次** |
| longtask p95 / max | 91 ms / 6603 ms（max 为开场模型加载，一次性） |
| 累计阻塞 | 126.4 s / 188 s（约 67% 墙钟时间） |
| 堆内存 | 5.4 → 5.8 MB（峰值 9.9），同样无增长趋势 |

**量化回答"同步推理是否构成用户可感知卡顿"**：
真实推理模式下，`FaceEngine.detect()` 在主循环内同步执行，每一帧都是一次
50–90ms 的长任务，主线程约 2/3 的时间被推理占用。但系统的节拍本来就是
"检测驱动"的（主循环 = 检测循环），交互事件在帧间仍可得到响应，
单帧阻塞 p95=91ms 处于"可察觉但不失控"的量级；真正的长时间阻塞只有
开场的模型加载（约 6.6s，一次性，已有"正在初始化"状态提示覆盖）。

**重要口径限定**：无头环境 `--disable-gpu` 下 GPU 委托实际跑在 SwiftShader
软件仿真上，71.7ms/帧**不代表真实显卡上的表现**（真实 GPU 上应显著更快，
见角色四无头实测 GPU 44.43ms、CPU 13.21ms 的同环境对照——那组数字来自
更短会话、模型已热的阶段）。本节结论应理解为"在无 GPU 加速的最坏情况下，
同步推理的阻塞程度"。

## 三、基于数据的两项决策

### 3.1 要不要把 detect() 迁到 Web Worker？——本轮不做原型，理由如下

数据确实显示长任务频繁（真实推理下每帧一次）。但综合评估后**不**在本轮
做 Worker 化原型：

1. **主循环是检测驱动的**：把 detect 移进 Worker，主线程空出来的时间也没有
   其他重负载工作可并行（图表是低频增量绘制），用户感知的"帧率"仍由检测速度决定；
2. **可行性未验证且成本高**：MediaPipe tasks-vision 在 Worker 内运行需要
   验证模型加载路径、WASM 线程策略、`OffscreenCanvas` 与帧数据
   （`transferable` VideoFrame/Bitmap）的兼容链，任何一环不通都要返工；
3. **本环境的测量值偏悲观**：SwiftShader 仿真下的 71ms 不等于目标机器
   （带真实 GPU 的答辩用笔记本）上的数值，先花大成本优化一个可能被硬件
   直接消除的问题，不符合"正确性 > 不破坏现有测试 > 可维护性 > 性能"的优先级；
4. 若未来实测确需优化，本报告给出的采集脚本（`perf-profile.mjs`）可以直接
   用于对比迁移前后的 p95/累计阻塞数据。

**如实声明**：这是"基于数据判断后选择不做"，不是"已验证 Worker 化无效"。

### 3.2 两个更小的评估点

**① `requestVideoFrameCallback()` 替换 setTimeout 轮询 —— 保持现状。**
实测层面：主循环每帧 70ms+ 的推理开销远大于视频帧去重轮询的成本，
rVFC 节省的"无效轮询"在总耗时里不可见；风险层面：rVFC 与合成器绑定，
在窗口遮挡/节能/无头环境会像 rAF 一样被降频——这正是 `render-loop.js`
文件头注释记录过的、PERCLOS 采样率失真不可接受的原因；且本项目的
时间戳处理历史上出过 P0 级 bug（状态机锁死，见《真人实测问题汇总.md》），
无收益地触碰时间语义不划算。列为未来候选优化，本轮不改。

**② COEP（Cross-Origin-Embedder-Policy）—— 不添加。**
按任务书要求先查 `web/vendor/inventory.json`：本地只有
`vision_wasm_internal`（单线程 SIMD）与 `vision_wasm_nosimd_internal`
两个构建，**没有多线程（threads）版 WASM**。COEP 的唯一收益场景是
解锁 SharedArrayBuffer 跑多线程 WASM，前提不存在，添加 COEP 只会给
资源加载增加约束而无性能收益。故不添加；若未来引入多线程构建，
需重跑集成测试验证资源加载后再开启。

## 四、结论汇总

| 问题 | 实测结论 |
|---|---|
| 长会话内存泄漏？ | **无**（60min，2–10MB GC 锯齿，峰值封顶） |
| 演示模式主线程阻塞？ | 可忽略（60min 仅 1 次 51ms） |
| 真实推理主线程阻塞？ | 显著但可接受（每帧 50–90ms 长任务，交互 p95≈91ms；测量环境为无 GPU 仿真，偏悲观） |
| Worker 化？ | 本轮不做原型；第四轮尖峰实验已给出可行性结论（见 §5） |
| rVFC 替换？ | 不替换（收益不可见 + 节流风险 + 时间戳回归风险） |
| COEP？ | 不添加（无多线程 WASM，收益前提不存在） |

## 五、Worker 可行性尖峰实验（第四轮建议③补充，2026-08-11）

第三轮留下的关键未知是"MediaPipe tasks-vision 能否在 Web Worker 内运行"。
本轮用临时尖峰页面（验证后已删除，未入库）在真实无头浏览器里实测，得到**带根因的确定结论**：

### 实验步骤与真实结果

| 阶段 | 结果 |
|---|---|
| 模块 Worker 内 `FilesetResolver.forVisionTasks()` | ✓ 成功（返回 wasmLoaderPath/wasmBinaryPath） |
| Worker 内 `FaceLandmarker.createFromOptions()` GPU/CPU 委托 | ✗ 均失败：`ModuleFactory not set.` |
| Worker 内直接 `import()` wasm 加载器 | 加载成功但 `self.ModuleFactory === undefined` |
| 主线程对照：同样直接 `import()` 该加载器 | 同样 `undefined` —— 证明是**作用域问题**，不是 Worker 特有 |
| 桥接尝试：fetch 加载器源码 + 间接 eval（全局作用域执行） | ✗ 被 CSP 拦截（`unsafe-eval` 不在 script-src） |

### 根因（源码级实证）

1. wasm 加载器 `vision_wasm_internal.js` 是 UMD 构建，`ModuleFactory` 用顶层 `var` 声明；
2. MediaPipe 内部的加载函数 `$h`：主线程用 `<script>` 标签注入（经典脚本作用域，
   `var` 挂到 window）、经典 Worker 用 `importScripts`（同理挂到 self）——都能工作；
3. 但 `vision_bundle.mjs` 是 ES 模块，Worker 侧**必须**用模块 Worker 才能 import；
   而模块 Worker 里没有 `importScripts`，`$h` 回退到动态 `import()`——
   ESM 顶层 `var` 不会挂到 `self`/`globalThis`，`self.ModuleFactory` 永远 undefined。

### 结论

**当前 vendor 构建 + 本项目 CSP 下，把 detect() 迁进 Web Worker 不可行**，
除非：(a) 放宽 CSP 允许 `unsafe-eval`（不可接受，破坏第二轮安全基线）；
(b) 修补/重新打包 MediaPipe 加载器使其把 ModuleFactory 挂到 globalThis；
(c) 升级到官方支持 Worker 的 tasks-vision 版本（需重新验证模型行为一致性）。
这把第三轮"不做 Worker 化"的决定从推测升级为**实证结论**；
若未来沿 (b)/(c) 路径推进，本报告 §2 的长任务采集脚本可直接用于迁移前后对比。
