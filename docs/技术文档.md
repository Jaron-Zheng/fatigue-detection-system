## 架构设计

### 六层处理流程

系统按六层结构处理数据，主数据流从视频帧出发，依次变成特征、指标、疲劳指数，最后送到界面。

```
输入：摄像头视频帧（默认目标 24 FPS）
  ↓
感知：FaceEngine（face-engine.js）— 关键点、表情系数与姿态矩阵
  ↓
特征：FeatureExtractor（features.js）— 眼、嘴与头部状态
  ↓
指标：IndicatorEngine（indicators.js）— 闭眼状态机与七项指标
  ↓
融合：FusionEngine（fusion.js）— 加权、平滑与等级判定
  ↓
响应：AlarmSystem（alarm.js）/ SessionRecorder（recorder.js）— 提醒与记录
  ↓
呈现：Dashboard（dashboard.js）— 检测、设置与报告
辅助：Calibrator（calibration.js）、QualityGate（quality.js）；统一配置：config.js
```

### 九个模块文件

| 模块类名 | 文件名 | 所属层 | 主要职责 |
|---|---|---|---|
| FaceEngine | `face-engine.js` | 感知层 | 封装模型加载、推理委派与运行期回退 |
| FeatureExtractor | `features.js` | 特征层 | 计算几何与语义双通道特征，合成闭眼度 |
| Calibrator | `calibration.js` | 特征层 | 5s 个性化基线标定，给出个体阈值与姿态零点 |
| QualityGate | `quality.js` | 特征层 | 六项数据质量检查，不可靠样本不计入统计 |
| IndicatorEngine | `indicators.js` | 指标层 | 眼睛状态机与滑动窗口统计，输出七项指标 |
| FusionEngine | `fusion.js` | 融合层 | 模糊加权融合、平滑、兜底与滞回分级 |
| AlarmSystem | `alarm.js` | 响应层 | 四级声光报警、语音提示与冷却抑制 |
| SessionRecorder | `recorder.js` | 响应层 | 逐帧记录与事件归档，生成报告与导出文件 |
| Dashboard | `dashboard.js` | 呈现层 | 界面渲染、参数设置与交互 |

> config.js 只存参数，不算业务模块。

### 为什么分层

- **可测试性**：每层输入输出都可以独立验证，特征层跟指标层各自重算互不影响
- **可重现性**：会话记录存的是原始特征序列，可以在不同参数下离线重放
- **论文友好**：每层对应一节，数据流向清晰

## 核心算法

### 1. PERCLOS

定义：观测窗口内闭合度 ≥ `eyeCloseOn`（默认 0.75）的时间占比。
窗口长度 20 秒（`perclosSec: 20`），按时间加权累计。

> **R4 变更**：从 30s 缩短到 20s，加快响应速度。

**闭合度融合**：
```javascript
closure_geo = (EAR_open − EAR) / (EAR_open − EAR_close)  // [0,1]
closure_sem = (blinkScore − baseline) / (0.92 − baseline)  // [0,1]
closure = 0.6 × closure_geo + 0.4 × closure_sem
```

**眼睛状态机**（带滞回）：
```
闭合度 ≥ 0.75（eyeCloseOn）  → 进入闭眼
闭合度 ≤ 0.6（eyeCloseOff） 或 语义通道 < 0.4  → 退出闭眼
```

滞回带 0.15 防止边界抖动。语义否决只用来提前结束，不用来阻止进入，
因为几何通道更灵敏，漏掉闭眼的**开始**代价更高。

> **R5 变更**：`eyeCloseOn` 从硬编码 0.80 抽出为可配置参数，下调至 0.75。
> NTHU-DDD 真实数据评测发现真实眨眼峰值闭合度 ≈ 0.78，差 0.02 不过线导致
> 眨眼漏检 → 眨眼率虚低 → 触发伪"低频嗜睡"信号。对抗场景余量：揉眼场景
> 融合闭合度峰值 ≈ 0.64，仍低于阈值。

**原设计的问题与改进**：

最初用的是 `0.7×(0.6×geo + 0.4×sem) + 0.3×max(geo, sem)`，
理由是"倾向判更闭以降低漏报"。但真人实测发现它会在头部俯仰时锁死——
几何通道在 EAR 跌破闭眼线后饱和为 1，导致融合值下界 = 0.6，恰好等于退出阈值，
**数学上到不了退出条件**。记录到一次 300ms 的眨眼被拉成 3.9 秒"持续闭眼"
并触发重度报警，期间语义通道从 0.745 回落到 0.296（睁眼水平）但没有分量。

改进：去掉 `max` 项，改用纯线性融合 `0.6×geo + 0.4×sem`，
并加入**语义否决**：闭眼状态期间若语义通道 < 0.40，直接结束闭眼。
复验时同一条件（11 秒、90% 的帧几何通道判闭眼）产出 0 次闭眼、0 次报警。

**时间加权窗口** (`ring-buffer.js`)：
```
PERCLOS = Σ(闭合时长ᵢ) / Σ(所有样本间隔ᵢ)
```
间隔 > 400ms（`maxSampleGapMs`）视为观测中断，该段不计入分母（避免把摄像头被遮挡的时间当作"睁眼"）。

### 2. 眨眼动力学

**时长分类**：
- 眨眼：60–500ms（`blinkMinMs` ~ `blinkMaxMs`）
- 长闭眼：≥ 500ms（`microsleepMs`），不混进眨眼时长的统计
- 危险闭眼：≥ 1800ms（`criticalClosureMs`）

**长闭眼不计入平均眨眼时长**：
实测发现 4.4 秒闭眼会把平均眨眼时长拉到 741ms（同期真实眨眼 166–375ms），
同一事件已被 PERCLOS 和最长闭眼计过分，再计一次是重复计分，
更糟的是会掩盖眨眼频率下降这个深度嗜睡信号。
现在只有 60–500ms 的正常眨眼参与平均时长计算。

**频率隶属度**（双侧函数，过高或过低都异常）：
```
正常区间 12–22 次/分 → 隶属度 0
< 12 次/分：线性上升，4 次/分以下满贡献（深度嗜睡）
> 22 次/分：线性上升，45 次/分以上满贡献（代偿性频繁眨眼）
```
频率类指标需观测满 15 秒（`rateReadyMs`）后参与判定，避免开局误判。

### 3. 哈欠检测

**判据**：MAR > 阈值（校准时记录的基线 MAR + 偏移量 `marOpenDelta`，默认 0.25）且**持续 ≥ 1.2 秒**（`yawnMinMs`）。

> **R5 调优**：`marOpenDelta` 从 0.35 降至 0.25。依据：NTHU-DDD 真实数据中睡眠剥夺者的
> 哈欠常为低幅压抑型，0.35 增量下无法越过阈值（整段哈欠 clip 事件数为 0）。
> 降到 0.25 后该类哈欠可注册，调优集 MCC 0.781→0.854。下限约束：再降到 0.20 以下
> 会把说话判成哈欠（0.25 是两类分布的分离点）。

持续时长过滤的作用：
- 实测中两次哈欠分别在张口后 1.26s / 1.31s 触发，正好落在设计值附近
- 说话、喝水等短暂张口不会触发（通常 < 800ms）

**不应期 3 秒**（`yawnRefractoryMs`）：一次哈欠内 MAR 会多次越过阈值，只报一次。

---

### 4. 点头检测

**判据**：pitch 角速度（度/秒）超过阈值 55°/s（`nodPitchVelDegPerSec`）且向下（负梯度）。

**去抖**：连续两次点头间隔 < 900ms（`nodRefractoryMs`）视为同一次。

实测中角速度 55–125°/s 的动作全部捕获，58–125°/s 合并后报 6 次。

**与注意力分散的区别**：
- 点头：瞬时动作，看角速度尖峰
- 注意力分散：持续状态，看偏离角 ≥ 25°（`headDeviationDeg`）且持续 ≥ 1.5s（`distractionMinMs`）

---

### 5. 头部姿态与数据质量

**数据质量门控** (`quality.js`)：
```
侧转 |yaw − yaw₀| > 38°  → 数据无效，暂停判定
侧倾 |roll − roll₀| > 28° → 数据无效
人脸太小 / 太偏 / 光照过暗 → 数据无效
```

**为什么不设 pitch 上限**：低头是疲劳信号，不能当坏数据丢弃。

**质量不合格期间的处理**：
- 指标值冻结，不参与 PERCLOS 时间累积
- 疲劳分数置为 `null`，仪表显示 `--`
- 质量不合格的时间单独累计，报告里单独列出"测不准"占比
- UI 提示：「头部侧转过大，请正对摄像头」

**语义否决**（`semanticOpenVeto: 0.40`）：
闭眼状态期间，若 blendshape 语义闭合度低于 0.40，立即判为睁眼，不再听几何通道（EAR）。
取值依据：真实闭眼期间语义闭合度 0.61~0.74，姿态假阳性期间 0.08~0.41 且随时间回落。

### 6. 融合与防抖

**七项指标权重** (CONFIG.fusion.weights)：

```javascript
{
  perclos: 0.34,      // 闭眼时间占比（PERCLOS）：核心指标
  closureDur: 0.23,   // 最长持续闭眼时长：微睡眠强信号
  yawn: 0.21,         // 哈欠频率（真实数据第一线索）
  blinkRate: 0.08,    // 眨眼频率相对基线的偏移
  nod: 0.08,          // 点头频率
  blinkDur: 0.04,     // 平均眨眼时长（疲劳时变长）
  headDev: 0.02,      // 头部/视线偏离占比
}
```

权重和为 1.0，对应百分制分数（加权求和后 ×100）。可在专业模式的敏感性分析里验证每个权重的贡献。

> **权重调优历程**：
> - 初始：PERCLOS 0.30 / 最长闭眼 0.20 / 哈欠 0.14 / 眨眼频率 0.10 / 点头 0.10 / 眨眼时长 0.08 / 头部偏离 0.08
> - 第一轮（合成消融）：headDev/blinkDur 贡献低，核心眼部指标合计 0.50→0.57
> - 第二轮（NTHU-DDD 真实数据）：哈欠是真实数据中最可靠的疲劳线索，
>   但 0.14 权重下纯哈欠片段封顶 14 分永远够不到轻度阈值。重组：yawn 0.14→0.21，
>   nod/blinkRate 各降至 0.08，blinkDur 0.04，headDev 0.02。效果：灵敏度 81.0%→85.7%，
>   特异度 92.6% 持平，MCC +0.042。

**四重防抖**：
```
1. 就绪门控：PERCLOS 观测 ≥ 5s 且 ≥ 50 样本前该项贡献为 0
   频率类指标观测不足 15s（rateReadyMs）时隶属度置 0
2. EMA 平滑：score = 0.18×新值 + 0.82×旧值（α = 0.18）
3. 分段钳位：等级阈值 清醒<24 / 轻度24-52 / 中度52-74 / 重度≥74
4. 逐级去抖：目标等级需连续 600ms（levelDwellMs）满足才生效；降级需滞回 6 分 + 逐级降一级
```

**等级最短保持**（防止反复微睡眠造成等级来回跳动）：
```
mild: ≥ 1000ms | moderate: ≥ 2500ms | severe: ≥ 6000ms
```

**趋势加速器**：跟踪 EMA 一阶导数，上升时给正向加成（+8 上限，`trendMaxBoost`），下降时给轻微阻尼（-2 下限，`trendMinBoost`）。
不对称设计：上升加速 > 下降阻尼，因为「早报 0.5 秒」的价值远大于「晚恢复 0.5 秒」的代价。

**安全兜底（长闭眼两档触发）**：
- 闭眼 ≥ 1.08 秒（`criticalClosureMs × 0.6` = 1800 × 0.6），原始分下限取 68，EMA 状态下限取 50，标记 `long_closure`
- 闭眼 ≥ 1.80 秒（`criticalClosureMs`），原始分下限取 92，EMA 状态下限取 68，标记 `critical_closure`
- 此分支绕开常规等待环节，不受驻留等待限制

## 参数取值依据

所有参数集中在 `web/js/config.js`，每个关键参数都附有注释说明来源。
以下是论文中需要交代的几个：

### EAR 闭眼阈值

**个性化校准**：取睁眼基线的 72% 作为闭眼线（`earCloseRatio: 0.72`），恢复线为 80%（`earOpenRatio: 0.80`）。

依据：校准期间采集 5 秒睁眼样本（`durationSec: 5`，按有效时长计而非墙上时间），
取中位数为基线。0.72 和 0.80 这两个数是本系统自己的相对 EAR 配置系数，
与 P80、P70 那类瞳孔遮盖比例之间没有线性换算关系。

**实测验证**：单被试校准后 EAR 基线 0.238–0.253，闭眼线 0.172–0.182，
真实闭眼时 EAR 谷值 0.010–0.068（基线的 4–27%），正常眨眼时 0.047–0.105
（基线的 19–42%），分离度清晰。

### 语义否决阈值 0.40

**作用**：闭眼状态期间，若 blendshape 语义闭合度 < 0.40，直接判为睁眼。

**取值依据**（单被试实测）：
```
真实闭眼期间      语义闭合度  0.61 ~ 0.75  且保持高位
姿态假阳性期间    语义闭合度  0.08 ~ 0.43  且随时间回落
```

取 0.40：真实闭眼一侧留 0.21 余量，假阳性一侧留 0.01 余量；
同时与进入条件所需的 0.50 形成 0.10 的滞回带，避免在边界反复开合。

**局限**：这是单被试标定值，跨人群适用性需要多被试标注数据验证。

### PERCLOS 窗口 20 秒

参考国标 GB/T 21972-2017《驾驶员瞌睡检测系统性能要求及检测方法》
与 NHTSA 文献常用的 30–90 秒窗口。本系统取 20 秒（`perclosSec: 20`），
在灵敏度与稳定性之间取得最佳平衡——窗口越长越平滑但响应越迟钝，
越短越灵敏但易受单次长眨眼影响。20 秒在模拟评测中灵敏度与延迟均优于 30/60 秒。

> **R4 变更**：从 30s 缩短到 20s，加快响应速度。

### 哈欠持续时长 1.2 秒

参考文献中哈欠典型持续 1–4 秒，说话、喝水通常 < 0.8 秒。
取 1.2 秒是因为实测两次哈欠分别在 1.26s / 1.31s 触发，正好验证了这个值。

### 安全兜底阈值

```
闭眼 ≥ 1.08 秒（criticalClosureMs × 0.6） → 中度（68 分）
闭眼 ≥ 1.80 秒（criticalClosureMs）          → 重度（92 分）
```

依据：100km/h 下，1 秒盲行约 28 米，1.8 秒盲行 50 米（半个足球场）。
国标 GB/T 21972 要求对"闭眼超过 1.5 秒"的情况给出报警。
这里取 1.08 / 1.80 是加了安全余量（约 0.7 倍，与人类反应时间同量级）。
实现：`criticalClosureMs` 为基准阈值（1800ms），0.6 倍处为中度兜底线。

## 实测结果

### 真人实测条件

- 被试：1 人（开发者本人）
- 环境：室内自然光，正对笔记本摄像头
- 测试场景：6 组对照实验，共约 8 分钟有效数据
- 校准：每次重启后个性化校准 5 秒（`durationSec: 5`，按有效时长计）

### 关键发现

#### 1. EAR 的姿态敏感性是方向不对称的

**俯仰方向（危险）**：
- 大幅俯仰时 60 帧中 56 帧（93%）EAR 跌破闭眼线
- 连续 11 秒、90% 的帧几何通道都说"闭眼"
- 原因：头部后仰时摄像头从下方看，上眼睑遮住更多可见眼球，
  同时眼睛垂直方向被投影压缩，EAR（眼高/眼宽）系统性下降

**侧转方向（安全）**：
- 侧转时 EAR 反而偏高，峰值冲到 0.7845（基线的 3.1 倍）
- 原因：侧转压缩了眼宽的投影，EAR 比值反而上升
- 影响：只会造成漏报（不报闭眼），不会误报

**对策**：
- 俯仰：用 blendshape 语义通道交叉验证，语义 < 0.40 时否决几何通道
- 侧转：超过 38° 由质量门控接管，标记数据无效，暂停判定

#### 2. 两个通道的分离度

单被试实测，EAR 基线 0.238–0.253、闭眼线 0.172–0.182、blendshape 基线 0.238–0.279：

| 场景 | EAR 谷值（占基线） | 语义通道峰值 | 行为特征 |
|---|---|---|---|
| **真实闭眼** | 0.010 ~ 0.068（4–27%） | 0.61 ~ 0.74 | 保持高位 |
| **姿态假阳性** | 0.130 ~ 0.175（52–69%） | 0.08 ~ 0.41 | 随时间回落 |

中间有 0.19 的空档。这是语义否决阈值取 0.40 的依据，
也是"为什么需要双通道而不是单靠 EAR"的直接证据。

#### 3. 各功能模块验证

| 模块 | 测试条件 | 结果 |
|---|---|---|
| 哈欠检测 | 2 次刻意哈欠 | 1.26s / 1.31s 触发，设计值 1.2s |
| 点头检测 | 连续点头 85 秒 | 58–125°/s，去抖后报 6 次 |
| 注意力分散 | 左右转头各 6 秒 | 两侧各报 1 次，时长 7.1s / 7.3s |
| 质量门控 | 侧转 > 38° | 145 帧全部标为无效，恢复后自动解除 |
| 语义否决 | 11 秒姿态压 EAR | 0 次误报（改动前产出 3.9 秒假闭眼 + 重度报警） |
| 眨眼统计 | 5 分钟会话 | 49 次，9.16 次/分，时长 83–375ms |
| PERCLOS | 静坐 5 分钟 | 均值 0.86%、峰值 2.24%，符合清醒状态 |

## 已知局限

### 1. EAR 对头部姿态敏感

大幅俯仰时 EAR 系统性偏低，90% 以上的帧跌破闭眼线。
缓解措施：双通道融合 + 语义否决（实测验证有效）、数据质量门控排除极端角度。
残留风险：质量门控不限制俯仰——因为低头是疲劳信号，不能当坏数据丢弃。

### 2. 参数为单被试标定值

语义否决阈值 0.40、融合权重、部分滞回带宽度取值依据来自单人实测，跨人群适用性未验证。
缓解措施：提供参数调节界面（专业模式滑块）、敏感性分析工具。

### 3. 准确率未经规模化验证

视频评测工具已就绪，但缺少多被试标注数据集。
系统在受控条件下可用（真人实测 8 分钟 0 次误报），但不能外推为普适准确率。

### 4. 主观标注的固有噪声

视频评测采用被试自评标签（正常/疲劳），等价于 KSS 量表的简化。
自评受主观因素影响，不同被试对"疲劳"的理解不一致。

### 5. 浏览器环境的性能限制

MediaPipe Face Landmarker 在笔记本 CPU 上约 10–15 FPS，
开启 GPU 委托可达 20–25 FPS。低于专用硬件（30 FPS 以上）。
（口径说明：本组数字为开发期间的粗档观察；论文表 5-1 的 17.1～28.8 FPS 为
交付前在指定三台设备上按整帧端到端口径的实测记录，两组测量条件不同，
不可直接互相换算。）
缓解措施：用时间加权窗口而不是帧数窗口。

## 评测方法论

### 混淆矩阵与准确率指标

系统提供视频离线评测工具（`evaluation.js` + `evaluator.js`），
按时间加权混淆矩阵评价：

```
              实际正常    实际疲劳
预测正常        TN         FN
预测疲劳        FP         TP

灵敏度 = TP / (TP + FN)      # 查全率，疲劳时报警的比例
特异度 = TN / (TN + FP)      # 正常时不误报的比例
准确率 = (TP + TN) / 总样本
```

**响应延迟**：从实际进入疲劳到系统报警的时间间隔。

### 视频评测操作流程

详见 [`视频评测指南.md`](视频评测指南.md)。简要步骤：

1. 录制一段视频（包含清醒与疲劳两个阶段）
2. 在评测界面逐段标注：拖动时间轴，点「标为正常」或「标为疲劳」
3. 系统以固定步长（默认 100ms）逐帧推理，输出逐点数据与指标汇总
4. 导出 CSV：`视频评测逐点数据_*.csv`（含每一帧的预测值与标签）、
   `视频评测指标汇总_*.csv`（混淆矩阵与准确率）

### 敏感性分析与权重消融

**敏感性分析**：把本次会话的指标序列在多组参数下离线重算，
找出"稳定平台区"——参数在某个范围内变化时，结论基本不变。

**权重消融**：逐项扣除某指标的贡献（权重置 0），观察分数变化，
量化每个特征的实际作用。

两个工具的输出都是 CSV 表，可直接用于论文插图。
