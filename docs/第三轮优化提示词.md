## 面向 Qwen3.8-Max 的执行适配说明

下面这份任务书本身是模型无关的工程任务，写给任何一个能读写文件、跑命令、有长时间自主执行能力的智能体都成立。但既然要交给 Qwen3.8-Max（2026 年 8 月正式发布，主打"长时自主编程与协作"的 Hybrid Agent 模型）执行，有几条专门针对它的调整，写在最前面，方便你（人类）核对，不用改动后面的正文：

1. **推理强度拉满。** 如果你的接入方式（DashScope API、Token Plan、Qoder、QoderWork 等）暴露了 `reasoning_effort` 参数，这个任务设成 `xhigh`。整份任务书要求的是十几个角色的多步骤系统性执行，不是一次性问答，官方也是把这类长任务当成这个模型的主打场景在推——推理强度调低会明显浪费它本来的优势。
2. **不用担心塞不下，全文一次喂给它就行。** Qwen3.8-Max 的上下文窗口官方口径在百万 token 量级（不同资料对精确数字有出入，但明显远超这份文档的体量），这份任务书全文一次性传入完全没问题，不需要拆成多轮，也不需要我帮你精简。具体怎么传（系统提示词/首条消息/附件）取决于你用的工具，内容本身不用因为这一点改动。
3. **把「任务台账」当成它真正会持续读写的工作队列，而不是写完就扔的记录。** Qwen3.8-Max 公开的案例显示，它在长达十几天的自主运行中依赖"状态机 + 任务队列"的模式持续工作，任务从待认领到执行中逐步推进；角色一要建的 `docs/第三轮任务台账.md` 正好是这个模式的轻量版。**要求它每完成一小步就回写台账状态，而不是攒到最后一次性汇总**——这既贴近它已经展现出的工作方式，也让你能在它运行过程中随时打开这份文件看进度，不用干等它"回复"你。
4. **证据要贴出来，不能只给结论。** 公开评测对 Qwen3.8-Max 的说法不算一致：推理能力普遍评价很强，但工具调用的实际可靠性有评测机构给出的排名并不靠前。这意味着它有能力"讲出一个听起来对的完成情况"，却不一定每次都真的可靠执行到位。所以在正文「执行规则」第 3 条"不虚构任何测试结果"之上再加一条硬要求：**任何一处声称"已完成/已通过"的地方，必须在台账或对应文档里贴出真实的命令输出片段（哪怕只贴关键几行），不能只写一个"✅ 已完成"**。角色十四复核时，没有原始输出佐证的完成声明一律视为未验证，退回去补证据。
5. **长时间自主运行没问题，但别真走开十几天不看它。** 官方案例里出现过接近半个月的连续自主运行、几百次提交的展示，但这是发布时挑出来的案例，不等于每次都这么顺利——这个模型现在也才发布一两周，社区里已经有反馈说实际表现和文档描述有出入。建议就按本任务书角色一到角色十四的阶段边界设检查点：角色一（基线）跑完看一眼台账，角色二/三（架构与类型）完成后再看一眼，不用全程盯着，但也别当成完全免监督的黑箱扔在一边。
6. **保持中文，不用降级表达。** Qwen 系列是中文原生模型，这份任务书全文的中文技术表达（术语、长句、破折号插入语）应该比翻译成英文喂给它效果更好，不需要转成英文或简化措辞。

## 第二部分 · 这一轮到底要做什么，以及为什么

上一轮任务书（`系统优化提示词.docx`）解决的是"从毛坯到能用、安全、有测试"。这一轮目标不同：把项目从**"审计过的合格品"**推进到**"工程成熟、有实证支撑、经得起答辩追问"**的水平。

我实际读代码、跑测试后，找到了三类目前的测试和文档都还没覆盖到的空间：

1. **"未验证" ≠ "不能验证"。** `docs/测试报告.md` 列了 7 项"未验证项"，理由几乎都是"无头浏览器拿不到摄像头权限"。但 Chromium 系浏览器实际支持用命令行参数注入一个从视频文件读取画面的假摄像头设备，这意味着其中至少几项"未验证"是可以用自动化方式真正验证掉的，不必永远停留在"未验证"。
2. **代码质量还有明确的下一层。** `web/js/app.js` 目前 1294 行、约 40 个方法，同时承担状态机、主循环、DOM 初始化、事件绑定、视图切换、渲染等多种职责，是典型的"上帝对象"；项目也还没有类型检查、lint、性能画像、无障碍自动化扫描这些能让工程质量再上一个台阶的能力。
3. **这终究是一篇本科毕业设计，不只是一个 Web App。** `真人实测问题汇总.md` 自己列出的待办事项包含"多被试验证"和"准确率验证"，但目前完全没有配套工具支撑这两件事；导出的 CSV/JSON 目前只是"数据"，没有任何工具能把它们变成论文里能直接用的图。这部分的价值不比代码优化低——它更贴近你（学生）真正要交付的东西：一篇论文和一场答辩。

下面的角色分工，全部围绕这三个方向展开，不是对上一轮任务书的重复。

## 第三部分 · 执行规则

1. **全程自主执行，不要中途停下来问我。** 遇到设计判断，按"正确性 > 不破坏现有测试 > 可维护性 > 性能 > 视觉与体验"的优先级自行决定，在最终报告里说明理由即可。
2. **不允许通过调整阈值 / 权重让指标"看起来更准"。** 算法参数只有在你复现出一个新的、有真实数据支撑的缺陷时才能改，且必须留下完整证据链（现象、复现条件、根因、修复、修复前后对比数据），风格对齐 `真人实测问题汇总.md`。
3. **不虚构任何测试结果。** 没有真正执行过的命令、没有真正跑过的浏览器、没有真正测过的路径，一律写"未验证"及具体原因，不写"已通过""已验证"。这是本项目目前做得最好的一点，不要退步。
4. **不破坏"零安装即可运行"的承诺。** `README.md` 明确写了"只用内置模块，不需要 npm install"。可以为开发工具链（类型检查、lint、E2E 测试）引入 `devDependencies`，但必须满足：
   - `npm start` / `npm run serve`（普通使用者和答辩现场的路径）永远不需要先跑 `npm install`；
   - 需要额外依赖的脚本（`npm run typecheck`、`npm run lint`、`npm run test:e2e` 等）要在 README 里清楚标注"仅开发者需要，需先执行一次 npm install"，且不能出现在一键启动脚本的执行路径里；
   - 这些依赖放进 `package.json` 的 `devDependencies`，不是 `dependencies`。
5. **每个角色的产出都要能被验证。** 新增脚本要真的跑一遍，新增文档要和代码一致，新增测试要真的执行并记录通过数量。
6. **保留全部现有功能，阶段性跑回归。** 提交前至少完整跑一次 `npm run verify`（应仍为 31/31）与 `node tools/integration-test.mjs`（应仍为 41/41），任何数字下降都必须先修复并说明原因，不能通过修改测试用例让它"通过"。
7. **善用现有基础设施，不要重复造轮子。** 项目已有 `tools/screenshot.mjs`（CDP 无头浏览器控制），下面很多新任务（摄像头模拟、无障碍扫描、性能画像）建议在它的基础上扩展，而不是另起一套无头浏览器控制逻辑。
8. **善用已经初始化的 git 仓库。** `.git` 目录已存在但没有任何提交。建议第一步就把当前状态提交为初始 commit 并打 tag（如 `v2.0.0-audited`），后续每个角色完成后单独提交，为「角色十一」的交付方式改造做铺垫。

### 角色二 · 软件架构重构工程师

定位：解决 `web/js/app.js` 的"上帝对象"问题，但不引入构建步骤、不引入前端框架——继续保持项目"打开一个 `<script type="module">` 就能跑"的特性。

背景：`app.js` 目前 1294 行、约 40 个方法，同时承担状态机（`State.IDLE/CALIBRATING/RUNNING` 等状态的流转判断分散在 `_beginCalibration`、`_finishCalibration`、`_beginRunning`、`stop`、`_cancelStart` 等十几个方法里，没有集中定义合法的状态迁移表）、主循环调度（`_startLoop`/`_frame`）、DOM 初始化、事件绑定、专业模式与主题切换、图表绘制调用、视图切换、数据导出。相比之下 `web/js/ui/` 下的 `dashboard.js`、`report.js`、`settings.js` 已经是不错的职责划分范例，问题主要集中在 `app.js` 自己。

任务：
1. 新增 `web/js/core/session-state-machine.js`，把目前分散在 `app.js` 各方法里的状态迁移逻辑显式化：定义合法状态集合、每个状态允许的迁移、迁移前置条件（guard，如"只有校准完成才能进入 RUNNING"）、迁移时触发的副作用钩子。这个模块必须是纯逻辑、不依赖 DOM，因此**可以直接被 `tools/regression-test.mjs` 单元测试**——补充覆盖全部合法迁移路径 + 至少 5 种非法迁移尝试（如"未校准直接 RUNNING""RUNNING 时重复 start"）的用例。
2. 把 `app.js` 改造成"组合根"：构造函数里组装 `state machine + FaceEngine + IndicatorEngine + FusionEngine + 各 UI 模块`，自身不再包含业务判断分支，只做转发。如果拆分后仍超过 500 行，说明拆得不够彻底，继续拆。
3. 主循环（`_startLoop`/`_frame`）与渲染调用可以独立拆到 `web/js/core/render-loop.js`，职责只剩"多久跑一次、跑什么函数"，具体逻辑由 `app.js` 传入回调。
4. **每完成一个模块的抽取就跑一次 `npm run verify`**，不要把所有拆分堆到最后一次性验证——那样出问题也定位不到是哪一步引入的。
5. 拆分不是目的，可测试性和可维护性才是：拆完之后，新抽出的状态机模块应该有专门的单元测试覆盖（此前 `app.js` 几乎完全没有被 `regression-test.mjs` 直接测试到，因为它耦合了 DOM）。

验收标准：`app.js` 行数与方法数显著下降（目标：500 行以内）；存在可被 Node 直接 `import` 测试（不需要 DOM mock）的状态机模块并有专属单元测试；重构前后 `npm run verify` 与集成测试结果不变（31/31、41/41）；截图取证工具跑一遍确认 UI 表现无变化。

背景：项目目前完全是无类型的原生 JS，`config.js` 里参数很多，一个数字或字段名打错不会在写代码时被发现，只会在运行时表现成诡异的疲劳误判——这正是 `真人实测问题汇总.md` 里配置合并类型污染问题的间接成因。

任务：

验收标准：`npm run typecheck`、`npm run lint` 可执行且有实际输出记录；删除 `node_modules` 后 `npm start` 依然可直接运行（要在报告里明确验证一次）；README 更新。

### 角色四 · 自动化仿真测试工程师（本轮价值最高的新增角色之一）

任务：
1. 准备一段测试用人脸视频（可用 `docs/视频评测指南.md` 提到的评测视频，或专门录一段包含"正常眨眼—刻意闭眼—哈欠—点头"片段的短视频），转换成 `.y4m` 格式；如果环境限制无法转换，退而求其次说明可行性限制，不要为了完成任务而假装转换成功。

3. 用这套基础设施重新评估 `docs/测试报告.md`"未验证项"表格里的相关条目，能验证的就验证，不能的写明具体卡在哪一步（比如"headless 环境下 WebGL 上下文创建失败"这种具体原因，而不是笼统的"无法测试"），尤其是"模型实际加载耗时与推理帧率""真实摄像头授权与实时检测"两项。

### 角色五 · 长时稳定性与性能剖析工程师

定位：解决"长会话（>30min）内存曲线"这项已知未验证项，并给出主线程阻塞情况的量化数据（当前推理在主循环里同步调用，`face-engine.js` 的 `detect()` 直接在 `_frame()` 里被调用，没有 Worker 隔离）。

2. 用 `PerformanceObserver({entryTypes: ['longtask']})` 采集主循环运行期间的长任务（>50ms 阻塞主线程），统计频率与最大耗时，和 `FaceEngine.avgInferMs` 的既有统计对照，量化回答"当前同步推理是否已经构成用户可感知的卡顿"。
3. 基于第 2 步的实测数据做判断，不要先入为主：
   - 若长任务频繁且耗时明显，评估把 `FaceEngine.detect()` 迁移到 Web Worker + `OffscreenCanvas` 的可行性（MediaPipe tasks-vision 是否支持在 Worker 内运行需要先验证），能做则做一个原型并对比迁移前后数据；不能做或成本过高就如实记录原因。
   - 若长任务数据本身不明显，明确写清楚"当前实现在实测数据下没有表现出主线程阻塞问题，暂不需要 Worker 化"——这比强行"优化"一个没问题的东西更诚实，也更有价值。
4. 顺带评估两个更小的点，同样先测再改：
   - `HTMLVideoElement.requestVideoFrameCallback()` 相比目前 `setTimeout` 轮询 `video.currentTime` 去重，能否减少无效轮询、拿到更准的帧呈现时间戳；如果替换，要对照 `真人实测问题汇总.md` 里和时间戳相关的历史 bug（P0 状态机锁死那类问题往往和时间处理有关），确保回归测试全过。
   - `Cross-Origin-Embedder-Policy` 目前未设置，页面不是 `crossOriginIsolated`。先确认 `web/vendor/tasks-vision/` 下是否存在多线程版本 WASM（查看 `inventory.json`），**只有确认存在且能带来实测性能提升时才添加 COEP**，添加后必须重跑集成测试确认没有破坏资源加载。

验收标准：产出 `docs/长时稳定性与性能剖析报告.md`，包含真实采样得到的内存曲线数据、长任务统计数据，以及基于数据做出的"要不要 Worker 化 / 要不要上 COEP"的结论与理由；所有结论标注数据来源（哪次运行、多长时间、什么参数）。
