### P2 背景与问题

**本页要点**
- 疲劳驾驶是交通事故的主要诱因之一，驾驶员在事发前通常已出现可观测的面部行为退化（闭眼变长、眨眼模式改变、哈欠、点头）
- 单一特征（如仅 PERCLOS）在墨镜、揉眼、说话等场景下易误判，需要多特征互证
- 现有方案多为本地安装的桌面软件或需上传视频的云端服务，部署与隐私成本高
- 本课题要回答的问题：能否在零安装、零上传的约束下，做出判别有效、误报可控、可分级报警的疲劳检测

**配图**：无现成图。可用 `docs/架构图.svg` 的局部做视觉支撑，或纯文字排版

**口播提示**：问题定义是本页重点——我不只做"能不能检测"，而是同时约束三个条件：免安装、不上传画面、报警可分级。

### P3 技术方案选型

**本页要点**
- 为什么 Web：免安装、跨平台、摄像头权限由浏览器安全上下文管控；全部依赖本地化后断网可用（模型 3.6MB + WASM 22MB，合计约 26MB，来源：README 隐私节）
- 为什么 MediaPipe Face Landmarker：单模型同时输出 478 关键点 + 52 blendshape + 姿态矩阵，几何通道与语义通道双路可用，WASM 推理可在浏览器内实时运行
- 为什么多特征融合：七类特征覆盖眼、嘴、头三个部位，单一特征被污染时由权重稀释与多信号互证兜底（对抗实验 6/6 零误报，〔实验报告 §5〕）
- 明确的代价陈述：融合系统带防抖与平滑，响应比瞬时阈值保守（〔实验报告 §2〕），这是抑制等级抖动的工程代价

**配图**：`figures/对抗场景误报.svg`（用 6/6 结果直接支撑"为什么融合"）

**口播提示**：三个选型各对应一问一答，重点是"为什么融合"——我用对抗实验的结果来回答，而不是只讲道理。

### P5 核心算法：特征层 → 指标层 → 融合层

**本页要点**
- 特征层：EAR / MAR / 欧拉角 / blendshape 语义系数，双通道输出
- 指标层：滑动窗口 + 状态机，把原始特征换算成七个指标
- 融合层：隶属函数归一化 → 加权求和 → EMA 平滑 → 四重防抖，输出 0–100 指数与四级等级
- 七特征与权重（〔config.js fusion.weights，合计 1.00〕）：

| 特征 | 权重 |
|---|---|
| PERCLOS（眼睛闭合时间占比） | 0.34 |
| 最长持续闭眼时长 | 0.23 |
| 眨眼频率相对基线偏移 | 0.10 |
| 平均眨眼时长 | 0.05 |
| 哈欠频率 | 0.14 |
| 点头频率 | 0.10 |
| 头部/视线偏离占比 | 0.04 |

- 权重取值可由权重消融实验验证（复现：`node tools/accuracy-eval.mjs` 第三节，PERCLOS 贡献 #1 / 最长闭眼 #2 / 哈欠 #3；〔实验报告 §3〕）

**配图**：`figures/权重消融贡献度.svg`（与权重表互印证）；`figures/会话疲劳指数时序.svg`（展示指数输出形态）

**口播提示**：重点讲权重不是拍脑袋——每个特征的贡献度有消融实验支撑，参数全部集中在 config.js 且带取值依据注释。

### P6 关键工程决策（三个亮点）

**本页要点**
- 亮点一：语义否决。EAR 几何通道在仰头时系统性失真（仰头约 14° 时 60 帧中 56 帧 EAR 跌破闭眼线，状态机永久卡在"闭眼"，300ms 眨眼被记成 3.9s）。引入 blendshape 语义闭合度否决，阈值 0.40：真实闭眼期间语义闭合度 0.61–0.74，姿态假阳性期间 0.08–0.41，取 0.40 对真实闭眼留 0.21 余量（全部数字来源：〔config.js semanticOpenVeto 注释〕）
- 亮点二：时间加权窗口（等级驻留 + EMA）。驻留时长 awake 0 / mild 1s / moderate 2.5s / severe 6s（〔config.js minHoldMs〕），叠加 EMA 平滑与滞回，抑制等级抖动；代价是响应更保守，已在基线对照中如实呈现（〔实验报告 §2〕）
- 亮点三：危险闭眼 override。持续闭眼 ≥1.8s 直接判重度并触发最高级报警，绕过融合平滑通道（〔config.js criticalClosureMs=1800〕；〔实验报告 §4〕：指数通道延迟与 override 通道分开讨论的依据）
- 三者关系：否决管"算得对"，驻留管"报得稳"，override 管"极端情况报得快"

**配图**：`figures/敏感性_危险闭眼时长.svg`（override 参数的敏感性平台区）；`figures/敏感性_EMA 平滑系数.svg`（平滑参数依据）

**口播提示**：这页是答辩的核心页，每个亮点都带实测数字，讲的时候先说问题（失真/抖动/极端延迟），再说机制，最后报数字。

### P8 实验与结果

**本页要点**
- 判别有效性：AUC = 0.99987，AP = 0.99996（43,650 采样点，正例 36,970 / 负例 6,680；疲劳指数 0–100 以 1 分步长扫 101 个工作点，AUC 为经验 ROC 梯形积分，与 Mann-Whitney U 恒等，回归测试 7.1 已交叉验证；〔实验报告 §1〕）
- 基线对照（同一数据同一口径，按采样点计数，〔实验报告 §2〕）：

| 方法 | 灵敏度 | 特异度 | F1 | MCC |
|---|---|---|---|---|
| PERCLOS ≥ 0.05 | 93.3% | 100% | 0.965 | 0.825 |
| PERCLOS ≥ 0.08 | 87.0% | 100% | 0.930 | 0.711 |
| 七特征融合（内置分界） | 86.4% | 100% | 0.927 | 0.702 |

- 基线结论的诚实陈述：合成数据上宽松瞬时 PERCLOS 的 F1 更高；融合价值从两点论证——对抗场景单特征污染时融合零误报，且能输出四级分级与归因（〔实验报告 §2〕论证角度 a/b）
- 检出延迟：10 个疲劳区间，检出 10、漏检 0，延迟均值 15.3s / 中位 16.9s；延迟来源 = PERCLOS 窗口固有累积 + EMA + 等级驻留，危险闭眼由 override 通道保证秒级响应（〔实验报告 §4〕）
- 对抗场景：6/6 PASS（低头看手机 / 频繁揉眼 / 说话 / 过减速带保持清醒且 450/450 帧误报 0%；戴墨镜 / 侧脸输出"信号不可用"而非猜测分；〔实验报告 §5〕）

**配图**：`figures/ROC曲线.svg` + `figures/PR曲线.svg`（判别力）；`figures/基线对比.svg`（对照）；`figures/混淆矩阵.svg`（工作点）；`figures/检出延迟.svg`；`figures/对抗场景误报.svg`

**口播提示**：这页信息量最大，建议只讲三个数：AUC 0.99987、延迟 15.3s 及其分解、对抗 6/6；基线对照主动讲，不要等老师问。

### P10 总结与创新点

**本页要点**
- 完成了什么：纯浏览器内七特征融合疲劳检测，零安装、零上传、断网可用，四级分级报警带 Top3 归因
- 创新点一：几何 + 语义双通道交叉验证（语义否决），用实测分离度定阈值，解决头部姿态导致的 EAR 系统性失真
- 创新点二：指数通道与 override 通道分离——常规状态靠时间加权窗口保稳，危险闭眼绕过平滑保快
- 创新点三：测不准时输出"信号不可用"而非猜测分（墨镜/侧脸场景），虚假安全感比明确的不可用更危险（〔实验报告 §5〕）
- 工程完成度：一键启动、PWA 离线、无障碍扫描、模糊测试、全量质量门禁（README 测试节）

## 二、答辩问答索引（Q1–Q7）

> 标准答案控制在 30 秒内说完；追问应对先给结论再给数据出处。

### Q1 准确率多少？

**标准答案**：演示数据上 AUC = 0.99987、AP = 0.99996（43,650 采样点，二分类口径为轻度及以上算疲劳），工作点指标以混淆矩阵报告：灵敏度 86.4%、特异度 100%、F1 0.927、MCC 0.702。

**支撑**：`figures/混淆矩阵.svg`、`figures/ROC曲线.svg`、`figures/PR曲线.svg`；复现 `node tools/accuracy-eval.mjs` 与 `node tools/analysis/confusion-chart.mjs docs-evidence/figures/accuracy-summary.csv`（〔实验报告 §1〕）。

**追问应对**
1. "AUC 怎么算的，为什么可信？"——疲劳指数 0–100 以 1 分步长扫 101 个工作点，AUC 为经验 ROC 梯形积分，与配对法 Mann-Whitney U 恒等（平局记 0.5），回归测试 7.1 有已知值断言与手工验算用例保护（〔实验报告 §1、§7〕）。
2. "数据是真实的吗？"——如实回答：演示数据为 SimulatedDriver 合成剧本，正式数字需用真实标注视频重跑同一命令；工具链已就绪，这是口径问题不是能力问题（〔实验报告 §头部声明、§2〕）。

### Q2 为什么不用简单的 PERCLOS 阈值？

**标准答案**：在合成演示数据上宽松瞬时 PERCLOS 阈值（≥0.05 时 F1 = 0.965）确实高于融合系统（0.927），我如实报告；但基线在墨镜、揉眼场景无解，且只能做二分类，融合可输出四级分级与归因，这是报警分级的前提能力。

**支撑**：`figures/基线对比.svg`；复现 `node tools/accuracy-eval.mjs`（〔实验报告 §2〕）。

**追问应对**
1. "融合 F1 更低怎么解释？"——两个原因：合成剧本疲劳段 PERCLOS 信号极强且干净，单特征即可线性分离；融合系统带等级驻留（mild 1s / moderate 2.5s / severe 6s）与 EMA，响应保守是抑制等级抖动的工程代价（〔实验报告 §2〕）。
2. "换真实数据结论会反过来吗？"——论证框架已备好：鲁棒性角度（对抗实验单特征污染时融合零误报，基线无解）+ 等级输出角度；真实数据重跑同一命令即可比较（〔实验报告 §2〕论证角度 a/b）。

### Q3 每个特征都有用吗（权重怎么定的）？

**标准答案**：用权重消融实验量化——扣除单一特征后观察平均疲劳指数的变化量，变化越大越依赖该特征，结果与 config.js fusion.weights 配置互印证。

**支撑**：`figures/消融实验.svg`；复现 `node tools/accuracy-eval.mjs`（第三节），界面入口为设置抽屉"运行权重消融实验"（〔实验报告 §3〕）。

**追问应对**
1. "权重是拍的还是实验定的？"——权重集中配置在 config.js 且带注释，消融实验提供贡献度验证；同时说明主要权重（PERCLOS 0.34、闭眼时长 0.23）与微睡眠/PERCLOS 的文献共识一致（〔config.js fusion.weights〕）。
2. "去掉某个特征系统会坏吗？"——消融测的是贡献度不是可用性；单特征被污染时系统靠权重稀释 + 多信号互证保持零误报（对抗实验 6/6，〔实验报告 §5〕），两个实验互为补充。

### Q4 报警来得及吗（延迟多少）？

**标准答案**：指数通道在演示数据上检出延迟均值 15.3s、中位 16.9s（10 个疲劳区间，检出 10、漏检 0），延迟来自 PERCLOS 滑动窗口固有累积 + EMA + 等级驻留；危险闭眼场景由 override 通道保证秒级响应（持续闭眼 ≥1.8s 直接判重度，绕过平滑），两个通道分开讨论。

**支撑**：`figures/检出延迟.svg`；复现 `node tools/accuracy-eval.mjs`（〔实验报告 §4〕；override 参数〔config.js criticalClosureMs〕）。

**追问应对**
1. "15.3 秒是不是偏长？"——如实承认方法固有特性，并给出三层缓解：override 通道对最危险的持续闭眼秒级响应；延迟口径为"疲劳区间起始到首次判轻度及以上"，保守的等级驻留拉高了它；报告建议论文同时报均值/中位数/最大值三组数（〔实验报告 §4〕）。
2. "override 会不会误报（正常眨眼触发）？"——正常眨眼远短于 1.8s（微睡眠判定线 0.5s，最高级报警线 1.8s，中间留了 1.3s 余量）；参数敏感性见 `figures/敏感性_危险闭眼时长.svg`（〔config.js microsleepMs/criticalClosureMs〕）。

### Q5 什么情况会误报？

**标准答案**：六个对抗场景（低头看手机、频繁揉眼、说话、过减速带、戴墨镜、侧脸）全部通过：前四个保持清醒且 450/450 帧误报 0%，后两个输出"信号不可用"而非猜测分。

**支撑**：`figures/对抗场景误报.svg`；复现 `node tools/accuracy-eval.mjs` 第五节（6/6 PASS，指标流直接喂给真实 IndicatorEngine + FusionEngine，每场景 450 帧≈15s、全程计入统计；〔实验报告 §5〕）。

**追问应对**
1. "实验设定是不是太理想？"——如实说明设定：驾驶员清醒时做出易致单一特征误判的非典型行为，喂给的是真实 FusionEngine 而非模拟结果；它验证的是融合的抗污染机制，不等于大规模真实场景误报率（〔实验报告 §5〕）。
2. "信号不可用算不算失效？"——不算，是设计决策：测不准时输出明确的不可用状态比输出猜测分更安全，虚假安全感比明确的不可用更危险；界面与报警层对该状态有专门呈现（〔实验报告 §5〕）。

### Q6 怎么解释结果（可解释性）？隐私怎么保证？

**标准答案**：每次报警附 Top3 贡献特征及实时分值（实测示例："主要贡献：闭眼时间占比 30.0 分、最长闭眼 20.0 分、哈欠频率 12.4 分"）；画面只在浏览器内存中处理，不上传、不落盘，分析完即丢弃。

**支撑**：归因链路 fusion.js topFactors → alarm-visuals.js notify（〔实验报告 §6〕）；隐私佐证：概览页"数据流向，全程可见。"原创 SVG、集成测试断言首页无外部域名请求、CSP/Permissions-Policy 响应头收紧（〔实验报告 §6〕）。

**追问应对**
1. "归因是事后算的还是报警时就有？"——报警时实时计算并附在通知里，不是事后分析；导出的 JSON 报告也带完整参数与事件列表（〔实验报告 §6〕；README 导出数据节）。
2. "'不上传'有什么证据，不只是承诺？"——三层证据：集成测试断言首页无外部域名请求（自动化验证）；全部依赖本地化，断网可用并经 PWA 断网实测 12/12 通过（README PWA 节）；本地服务器只提供静态文件、不接收上传（README 隐私节）。

### Q7 工程质量如何？

**标准答案**：`npm run verify:full` 一条命令跑完静态检查 + 回归测试 138 项 + 集成/安全测试 41 项 + typecheck/lint 0 errors；另有无障碍扫描、模糊测试（默认 1000 轮随机剧本）、长会话性能剖析等第三轮脚本。

**支撑**：〔实验报告 §7〕；性能与稳定性数字见〔性能报告 §一、§二〕；复现 `npm run verify:full`。

**追问应对**

### 3.3 打包命名规范与校验文件生成

**命名规范**：`毕业设计交付_姓名_日期.zip`（日期格式 YYYYMMDD，例：`毕业设计交付_张三_20260601.zip`）。

**打包（Windows PowerShell，在项目根目录执行）**：

```powershell
Compress-Archive -Path 一键启动.bat,一键启动.ps1,package.json,server,tools,web,docs,docs-evidence,演示视频,交付说明.txt `
  -DestinationPath "毕业设计交付_张三_20260601.zip" -Force
```

**SHA256 校验文件生成（PowerShell）**：

```powershell
Get-FileHash "毕业设计交付_张三_20260601.zip" -Algorithm SHA256 |
  Select-Object Algorithm,Hash,Path |
  Out-File "毕业设计交付_张三_20260601.zip.sha256" -Encoding utf8
```

**接收方核验（PowerShell）**：

```powershell
(Get-FileHash "毕业设计交付_张三_20260601.zip" -Algorithm SHA256).Hash
# 输出与 .sha256 文件中的 Hash 字段比对，一致即包完整
```

注意：打包前先跑一遍 3.2 自检表全部六项，任何一项不通过不打包；zip 与 .sha256 两个文件成对交付。
