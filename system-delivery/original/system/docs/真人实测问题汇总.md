# 真人实测问题汇总

本文档记录 2024 年 1 月开发期间，通过真人实测发现并修复的 9 个问题。
所有问题均已修复并用实测数据验证。

## 测试条件

- **被试**：1 人（开发者本人）
- **环境**：室内自然光，笔记本摄像头
- **测试场景**：6 组对照实验
  - 空房间无人（1 分 33 秒）
  - 基线静坐（45 秒）
  - 刻意闭眼 3 秒 × 2
  - 打哈欠 × 2
  - 点头 × 多次
  - 仰头/低头保持（验证姿态敏感性）
  - 左右转头（验证侧转处理）
- **有效数据**：约 8 分钟
- **校准**：每次重启后个性化校准 8 秒

## 问题清单（按严重程度排序）

### P0 — 眼睛状态机在头部俯仰时锁死

**现象**：一次 300ms 的正常眨眼在头部后仰后被拉成 3.9 秒"持续闭眼"，触发重度疲劳报警。

**复现条件**：头部后仰约 23°，保持 8 秒。期间眼睛正常睁开、正常眨眼。

**根因**：
原融合公式 `closure = 0.7×(0.6×geo + 0.4×sem) + 0.3×max(geo, sem)`，
其中 `geo` 为几何通道（EAR），`sem` 为语义通道（blendshape 的 eyeBlink）。

头部后仰时，摄像头从下方看，上眼睑遮住更多可见眼球，EAR 系统性下降。
实测中 11 秒内 60 帧有 56 帧（93%）EAR 跌破闭眼线。

**几何通道在 EAR 跌破闭眼线后饱和为 1.0**，因此融合值下界 = 0.6×1.0 + 0.3×1.0 = 0.9，
而退出条件是 `closure ≤ 0.60` —— **数学上永远到不了退出条件**。

期间语义通道从 0.745 一路回落到 0.296（睁眼水平），全程在说"眼睛是开的"，
但在原公式里它的权重不足以把总分压到 0.60 以下。

**修复方案**：
1. 去掉 `max` 项，改用纯线性融合 `closure = 0.6×geo + 0.4×sem`
2. 加入**语义否决**：闭眼状态期间，若 `sem < 0.40`，立即判为睁眼

否决阈值 0.40 的依据：
```
真实闭眼期间      语义通道  0.61 ~ 0.75  且保持高位
姿态假阳性期间    语义通道  0.08 ~ 0.43  且随时间回落
```
取 0.40 正好落在空档中间，两侧各留约 0.1 余量。

**验证结果**：
同一条件（11 秒、90% 的帧几何通道判闭眼）下，修复后产出 **0 次长闭眼、0 次报警**。

**影响代码**：
- `web/js/core/indicators.js`（闭合度融合 + 状态机退出条件）
- `web/js/config.js`（新增 `quality.semanticOpenVeto` 参数）

### P0 — 摄像头前没人时报告说"状态良好"

**现象**：空房间无人运行 1 分 33 秒，报告结论：「清醒 100.0%，未发现明显疲劳特征。」

**根因**：人脸检测失败时，系统内部标了 `unreliable`，但这个标记没有传递到
分数计算与时间统计——分数被 EMA 平滑拉回 0，等级判为「清醒」，
时间计入"清醒 100%"。

**期望行为**：测不准的时间不应该计入任何等级，报告标题应该是
「本次检测未能得出结论」而不是「清醒」。

**修复方案**：
1. 新增 `CONFIG.fusion.gateFusion` 开关（默认 `true`）：
   数据无效时分数置为 `null`，不参与 EMA，不计入等级时长
2. 仪表盘：分数为 `null` 时显示 `--`
3. 报告：测不准占比 > 50% 时，标题变为「未能得出结论」

**验证结果**：
同样场景重测，报告显示「清醒 0.0%、测不准 100%」，标题「未能得出结论」。

**影响代码**：
- `web/js/core/fusion.js`（分数计算）
- `web/js/core/recorder.js`（时间统计与报告标题）
- `web/js/ui/dashboard.js`（仪表显示）
- `web/js/config.js`（新增 `fusion.gateFusion`）

### P1 — 长闭眼污染平均眨眼时长

**现象**：一次 4.4 秒闭眼被算进"平均眨眼时长"，导致均值从 166–375ms 拉到 741ms。

**根因**：所有闭眼结束时都调用 `_closeEyeEpisode`，在里面判断是眨眼还是微睡眠，
然后都推进 `blinkWin` 事件窗口。微睡眠（500–1800ms）和危险闭眼（≥1800ms）
也被当作"眨眼"参与平均时长计算。

**为什么错**：
- 同一事件已被 PERCLOS 和最长闭眼计过分，重复计分
- 更糟的是会掩盖眨眼频率下降这个深度嗜睡信号（4.4 秒的"眨眼"拉低了眨眼率）

**修复方案**：
只有 60–500ms 的正常眨眼才推进 `blinkWin`，微睡眠和危险闭眼只上报事件、不参与统计。

**验证结果**：
实测 5 分钟会话，49 次眨眼，均值 180ms，全部落在正常区间（83–375ms）。

**影响代码**：
- `web/js/core/indicators.js`（`_closeEyeEpisode` 方法）

### P1 — 保存的参数刷新后不生效

**现象**：用户在设置面板里调整参数并保存，刷新页面后参数恢复默认值。

**根因**：`app.js` 的初始化顺序错误：
```javascript
constructor() {
  this.buildSettings();   // 构造设置面板，此时滑块按默认值创建
  this.loadUserConfig();  // 从 localStorage 读取用户参数 ← 太晚了
}
```

滑块已经按默认值建好，`loadUserConfig()` 只改了内存里的 `CONFIG` 对象，
没有触发滑块的 `value` 更新。

**修复方案**：
调整初始化顺序，先加载用户配置，再构造界面：
```javascript
constructor() {
  this.loadUserConfig();  // 先加载
  this.buildSettings();   // 再构造，此时 CONFIG 已是用户值
}
```

**验证结果**：
调整参数 → 保存 → 刷新，滑块位置、图表时间窗口、配置导出全部一致。

**影响代码**：
- `web/js/app.js`（构造函数）

### P2 — face_lost 事件风暴

**现象**：一次 6 秒转头产生 **8 组** `face_lost` / `face_found` 事件，
其中多对间隔不到 100 毫秒：
```
44.1s face_lost → 44.1s face_found
44.5s face_lost → 44.6s face_found
47.0s face_lost → 47.0s face_found
```

**根因**：`face_lost` 在第一个丢帧就上报，`face_found` 在第一个恢复帧就上报，
完全没有去抖。侧转到检测边界时检测器逐帧闪烁，就变成事件风暴。

**为什么需要去抖**：
事件风暴刷满时间轴，报告里"没看到人脸"次数被虚增成 8 次，
而实际只是一次持续的大角度侧转。

**为什么内部状态不能去抖**：
人脸丢失时必须**立刻**冻结眼睛状态机、中断 PERCLOS 累积，
这些关系到"不要把丢失误算成闭眼"与"不要把中断期当作状态延续"，
属于数据完整性，不能为了少写几条日志而延迟。

**修复方案**：
只延迟**上报**，不延迟**处理**：
- 增加 `CONFIG.event.faceLostReportMs = 400`（去抖门限）
- 增加 `this._faceLostReported` 标志位
- 丢失持续 ≥ 400ms 才上报 `face_lost`
- 只有真的报过"丢失"才配一条"恢复"（且带实际时长）

**验证结果**：
同一动作，修复后变成 **2 组**（左右各一次），
事件日志：`29.0s face_lost` → `35.2s face_found 6585ms`。

**影响代码**：
- `web/js/core/indicators.js`（人脸丢失处理逻辑）
- `web/js/config.js`（新增 `event.faceLostReportMs`）

### P2 — CSV 负数被写成文本

**现象**：导出的 CSV 里 pitch / yaw / roll 三列的负数被写成 `'-3.86` 
（前置单引号），Excel 识别成文字列，无法求平均、无法画图。

**根因**：`recorder.js` 的 `_csvEscape` 函数对所有值都加单引号：
```javascript
return `'${String(v).replace(/'/g, "''")}`  // 错误
```

这是为了防止逗号、换行符破坏 CSV 结构，但对数值列不应该加。

**修复方案**：
只对字符串加引号，数值直接写：
```javascript
_csvEscape(v) {
  if (v === null || v === undefined) return '';
  if (typeof v === 'number') return String(v);  // 数值直接写
  const s = String(v);
  if (s.includes(',') || s.includes('\n') || s.includes('"')) {
    return `"${s.replace(/"/g, '""')}"`;
  }
  return s;
}
```

**验证结果**：
导出后 Excel 双击打开，pitch / yaw / roll 列正确识别为数值，
可直接插入"求和"公式，可直接插入图表。

**影响代码**：
- `web/js/core/recorder.js`（`_csvEscape` 方法）

### P2 — CSV 英文表头

**现象**：导出的四个 CSV 文件表头全是英文，不符合中文毕业论文的附录要求。

**期望行为**：表头中文化，但要保证离线复现能读回自己和旧版的文件。

**修复方案**：

- 往返：导出后再导入，样本数、首行等级、时间戳全部一致
- 兼容：旧版英文表头的 CSV 仍可导入

**影响代码**：

### P3 — 人脸丢失期间 CSV 标记数据有效

**现象**：导出的 CSV 里，人脸检测失败的行「数据是否有效」列写的是 `1`。

**为什么错**：人脸都没检测到，这一行不该标成有效观测。
拿去做数据分析的人会把这些行当成正常数据。

**修复方案**：
`indicators.js` 的人脸丢失分支里，`return this._snapshot(ts, feat, calib, false)` 
改为 `return this._snapshot(ts, feat, calib, false, false)`，
显式传入 `dataValid = false`。

**验证结果**：
导出 CSV，人脸丢失期间「数据是否有效」列全部为 `0`。

**影响代码**：
- `web/js/core/indicators.js`（人脸丢失分支）

### P3 — 建议文案用绝对次数

**现象**：报告建议写「记录到 3 次点头动作，可能已进入间歇性打盹」，
实际会话时长 5 分钟，频率只有 0.56 次/分，属于正常的看仪表、活动脖子。

**根因**：判据用的是绝对次数 `>= 3`，会话越长越容易误触。

**修复方案**：
改用频率判据：
```javascript
if (counts.nod >= 3 && counts.nod / minutes >= 1.5) {
  lines.push(`记录到 ${counts.nod} 次点头动作（约 ${(counts.nod / minutes).toFixed(1)} 次/分），可能已进入间歇性打盹。`);
}
```

1 分钟内 3 次（3 次/分）才是打盹征兆，5 分钟内 3 次（0.6 次/分）是正常活动。

**验证结果**：
相同数据重新生成报告，点头与分心的建议都带上了频率，不再误判。

**影响代码**：
- `web/js/core/recorder.js`（报告建议生成）

### 人脸丢失时质量胶囊显示过期原因

**现象**：人脸检测失败时，质量状态胶囊仍显示「头部侧转过大」之类的提示，
但那是丢失前的旧值，此刻的真正原因是"没看到人脸"，应该由旁边的人脸状态胶囊负责说。

**修复方案**：
`dashboard.js` 的 `_updateQualityPill` 里，`facePresent === false` 时直接隐藏质量胶囊。

**影响代码**：
- `web/js/ui/dashboard.js`
