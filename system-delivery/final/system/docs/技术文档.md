## 架构设计

### 分层数据流

```
摄像头 → 特征层 → 指标层 → 融合层 → 报警/展示/记录
```

**特征层** (`features.js`)  
从 478 关键点、52 blendshape、4×4 姿态矩阵中提取：
- EAR（Eye Aspect Ratio，几何通道）
- blendshape 的 eyeBlink 系数（语义通道）
- MAR（Mouth Aspect Ratio）
- 欧拉角 pitch / yaw / roll

**指标层** (`indicators.js`)  
基于滑动窗口和状态机：
- PERCLOS（P80 定义）
- 闭眼时长分类（眨眼 / 微睡眠 / 危险闭眼）
- 眨眼率（窗口内次数 / 时长）
- 哈欠检测（持续张口 ≥ 1.2s）
- 点头检测（pitch 角速度阈值 + 去抖）
- 注意力分散（头部偏离 ≥ 25° 持续 ≥ 1.5s）

**融合层** (`fusion.js`)  
隶属函数 + 加权求和 + EMA 平滑 + 四重防抖：
```
score = (w₁·PERCLOS + w₂·avgBlink + w₃·blinkRate + w₄·yawnRate + w₅·nodRate + w₆·deviation) × 100
```
然后分段钳到安全区间、逐级防抖。

### 为什么分层

- **可测试性**：每层输入输出都可以独立验证，特征层跟指标层各自重算互不影响
- **可重现性**：会话记录存的是原始特征序列，可以在不同参数下离线重放
- **论文友好**：每层对应一节，数据流向清晰

## 核心算法

### 1. PERCLOS（P80）

定义：观测窗口内闭合度 ≥ 0.8 的时间占比。

**闭合度融合**（改进版）：
```javascript
closure_geo = (EAR_open − EAR) / (EAR_open − EAR_close)  // [0,1]
closure_sem = (blinkScore − baseline) / (0.92 − baseline)  // [0,1]
closure = 0.6 × closure_geo + 0.4 × closure_sem
```

**原设计的问题**：最初用的是 `0.7×(0.6×geo + 0.4×sem) + 0.3×max(geo, sem)`，
理由是"倾向判更闭以降低漏报"。但真人实测发现它会在头部俯仰时锁死——
几何通道在 EAR 跌破闭眼线后饱和为 1，导致融合值下界 = 0.6，恰好等于退出阈值，
**数学上到不了退出条件**。记录到一次 300ms 的眨眼被拉成 3.9 秒"持续闭眼"
并触发重度报警，期间语义通道从 0.745 回落到 0.296（睁眼水平）但没有分量。

**改进**：去掉 `max` 项，改用纯线性融合 `0.6×geo + 0.4×sem`，
并加入**语义否决**：闭眼状态期间若语义通道 < 0.40，直接结束闭眼。
复验时同一条件（11 秒、90% 的帧几何通道判闭眼）产出 0 次闭眼、0 次报警。

**眼睛状态机**（带滞回）：
```
闭合度 > 0.8  → 进入闭眼
闭合度 < 0.6 或 语义通道 < 0.4  → 退出闭眼
```

滞回带 0.2 防止边界抖动。语义否决只用来提前结束，不用来阻止进入，
因为几何通道更灵敏，漏掉闭眼的**开始**代价更高。

**时间加权窗口** (`ring-buffer.js`)：
```
PERCLOS = Σ(闭合时长ᵢ) / Σ(所有样本间隔ᵢ)
```
间隔 > 500ms 视为观测中断，该段不计入分母（避免把摄像头被遮挡的时间当作"睁眼"）。

### 2. 眨眼动力学

**时长分类**：
- 眨眼：60–500ms
- 微睡眠：500–1800ms
- 危险闭眼：≥ 1800ms

**长闭眼不计入平均眨眼时长**：
实测发现 4.4 秒闭眼会把平均眨眼时长拉到 741ms（同期真实眨眼 166–375ms），
同一事件已被 PERCLOS 和最长闭眼计过分，再计一次是重复计分，
更糟的是会掩盖眨眼频率下降这个深度嗜睡信号。
现在只有 60–500ms 的正常眨眼参与平均时长计算。

**频率归一化**：
```
f_norm = (f − 6) / (20 − 6)  // [0,1]，f 为次/分
```
6 次/分以下视为深度嗜睡，20 次/分为警觉状态下限。

---

### 3. 哈欠检测

**判据**：MAR > 阈值（校准时记录的 95 分位 + 偏移量 0.16）且**持续 ≥ 1.2 秒**。

持续时长过滤的作用：
- 实测中两次哈欠分别在张口后 1.26s / 1.31s 触发，正好落在设计值附近
- 说话、喝水等短暂张口不会触发（通常 < 800ms）

**不应期 3 秒**：一次哈欠内 MAR 会多次越过阈值，只报一次。

---

### 4. 点头检测

**判据**：pitch 角速度（度/秒）超过阈值 55°/s 且向下（负梯度）。

**去抖**：连续两次点头间隔 < 900ms 视为同一次。

实测中角速度 55–125°/s 的动作全部捕获，58–125°/s 合并后报 6 次。

**与注意力分散的区别**：
- 点头：瞬时动作，看角速度尖峰
- 注意力分散：持续状态，看偏离角 ≥ 25° 且持续 ≥ 1.5s

---

### 5. 头部姿态与数据质量

**数据质量门控** (`quality.js`)：
```
侧转 |yaw − yaw₀| > 38°  → 数据无效，暂停判定
侧倾 |roll − roll₀| > 28° → 数据无效
人脸太小 / 太偏 / 光照过暗 → 数据无效
```

**为什么不设 pitch 上限**：低头是疲劳信号，不能当坏数据丢弃。

**质量不合格期间的处理**：
- 指标值冻结，不参与 PERCLOS 时间累积
- 疲劳分数置为 `null`，仪表显示 `--`
- 质量不合格的时间单独累计，报告里单独列出"测不准"占比
- UI 提示：「头部侧转过大，请正对摄像头」

---

### 6. 融合与防抖

**权重** (CONFIG.fusion.weights)：
```javascript
{
  perclos: 42,       // PERCLOS 是主导指标
  avgBlinkMs: 18,    // 眨眼时长
  blinkRate: 16,     // 眨眼频率
  yawnRate: 12,      // 哈欠频率
  nodRate: 7,        // 点头频率
  headDeviation: 5   // 注意力分散占比
}
```

权重和为 100，对应百分制分数。可在专业模式的敏感性分析里验证每个权重的贡献。

**四重防抖**：
```
1. 初期保护：前 20 秒不报警（等待基线稳定）
2. EMA 平滑：score = 0.6×新值 + 0.4×旧值（α = 0.6）
3. 分段钳位：清醒时上限 20 分、轻度时上限 48 分（防止偶发尖峰直接跳到中/重度）
4. 逐级去抖：从清醒→轻度需连续 8 秒 > 20 分，从轻度→中度需连续 12 秒 > 48 分
```

**安全兜底**：
- 闭眼 ≥ 1.08 秒，直接钳到 68 分（中度），无论其他指标如何
- 闭眼 ≥ 1.80 秒，直接钳到 92 分（重度）

## 参数取值依据

所有参数集中在 `web/js/config.js`，每个关键参数都附有注释说明来源。
以下是论文中需要交代的几个：

### EAR 闭眼阈值

**个性化校准**：取睁眼基线的 72% 作为闭眼线。

依据：校准期间采集 8 秒睁眼样本，取中位数为基线。0.72 这个比例来自
经验——大部分人闭眼时 EAR 会降到睁眼基线的 60–75%，取 72% 在灵敏度与
鲁棒性之间取平衡。若取太高（如 0.80），正常眨眼可能检测不到；
若取太低（如 0.60），轻微低头就会触发假阳性。

**实测验证**：单被试校准后 EAR 基线 0.238–0.253，闭眼线 0.172–0.182，
真实闭眼时 EAR 谷值 0.010–0.068（基线的 4–27%），正常眨眼时 0.047–0.105
（基线的 19–42%），分离度清晰。

### 语义否决阈值 0.40

**作用**：闭眼状态期间，若 blendshape 语义闭合度 < 0.40，直接判为睁眼。

**取值依据**（单被试实测）：
```
真实闭眼期间      语义闭合度  0.61 ~ 0.75  且保持高位
姿态假阳性期间    语义闭合度  0.08 ~ 0.43  且随时间回落
```

取 0.40：真实闭眼一侧留 0.21 余量，假阳性一侧留 0.03 余量；
同时与进入条件所需的 0.50 形成 0.10 的滞回带，避免在边界反复开合。

**局限**：这是单被试标定值，跨人群适用性需要多被试标注数据验证。
论文中应作为已知局限如实说明。

### PERCLOS 窗口 60 秒

参考国标 GB/T 21972-2017《驾驶员瞌睡检测系统性能要求及检测方法》
与 NHTSA 文献常用的 30–90 秒窗口，取中间值 60 秒。

### 哈欠持续时长 1.2 秒

参考文献中哈欠典型持续 1–4 秒，说话、喝水通常 < 0.8 秒。
取 1.2 秒是因为实测两次哈欠分别在 1.26s / 1.31s 触发，正好验证了这个值。

### 安全兜底阈值

```
闭眼 ≥ 1.08 秒 → 中度（68 分）
闭眼 ≥ 1.80 秒 → 重度（92 分）
```

依据：100km/h 下，1 秒盲行约 28 米，1.8 秒盲行 50 米（半个足球场）。
国标 GB/T 21972 要求对"闭眼超过 1.5 秒"的情况给出报警。
这里取 1.08 / 1.80 是加了安全余量（约 0.7 倍，与人类反应时间同量级）。

## 实测结果

### 真人实测条件

- 被试：1 人（开发者本人）
- 环境：室内自然光，正对笔记本摄像头
- 测试场景：6 组对照实验，共约 8 分钟有效数据
- 校准：每次重启后个性化校准 8 秒

### 关键发现

#### 1. EAR 的姿态敏感性是方向不对称的

**俯仰方向（危险）**：
- 大幅俯仰时 60 帧中 56 帧（93%）EAR 跌破闭眼线
- 连续 11 秒、90% 的帧几何通道都说"闭眼"
- 原因：头部后仰时摄像头从下方看，上眼睑遮住更多可见眼球，
  同时眼睛垂直方向被投影压缩，EAR（眼高/眼宽）系统性下降

**侧转方向（安全）**：
- 侧转时 EAR 反而偏高，峰值冲到 0.7845（基线的 3.1 倍）
- 原因：侧转压缩了眼宽的投影，EAR 比值反而上升
- 影响：只会造成漏报（不报闭眼），不会误报

**对策**：
- 俯仰：用 blendshape 语义通道交叉验证，语义 < 0.40 时否决几何通道
- 侧转：超过 38° 由质量门控接管，标记数据无效，暂停判定

**论文建议**：这个不对称性值得单独成段，配分桶统计表。
它解释了为什么需要双通道融合，以及为什么侧转与俯仰的处理策略不同。

#### 2. 两个通道的分离度

单被试实测，EAR 基线 0.238–0.253、闭眼线 0.172–0.182、blendshape 基线 0.238–0.279：

| 场景 | EAR 谷值（占基线） | 语义通道峰值 | 行为特征 |
|---|---|---|---|
| **真实闭眼** | 0.010 ~ 0.068（4–27%） | 0.61 ~ 0.75 | 保持高位 |
| **姿态假阳性** | 0.130 ~ 0.175（52–69%） | 0.08 ~ 0.43 | 随时间回落 |

中间有 0.19 的空档。这是语义否决阈值取 0.40 的依据，
也是"为什么需要双通道而不是单靠 EAR"的直接证据。

#### 3. 各功能模块验证

| 模块 | 测试条件 | 结果 |
|---|---|---|
| 哈欠检测 | 2 次刻意哈欠 | 1.26s / 1.31s 触发，设计值 1.2s |
| 点头检测 | 连续点头 85 秒 | 58–125°/s，去抖后报 6 次 |
| 注意力分散 | 左右转头各 6 秒 | 两侧各报 1 次，时长 7.1s / 7.3s |
| 质量门控 | 侧转 > 38° | 145 帧全部标为无效，恢复后自动解除 |
| 语义否决 | 11 秒姿态压 EAR | 0 次误报（改动前产出 3.9 秒假闭眼 + 重度报警） |
| 眨眼统计 | 5 分钟会话 | 49 次，9.16 次/分，时长 83–375ms |
| PERCLOS | 静坐 5 分钟 | 均值 0.86%、峰值 2.24%，符合清醒状态 |

#### 4. 数据完整性验证

- CSV 中文表头往返无损（带 UTF-8 BOM，Excel 双击可开）
- 离线复现：导出后再导入，样本数、首行等级、时间戳全部一致
- 负数保持数值（之前用 `'-3.86` 会变成文本列）
- 人脸丢失期间 `dataValid` 正确标为 0

## 已知局限

写论文时必须如实说明的部分：

### 1. EAR 对头部姿态敏感

**问题**：大幅俯仰时 EAR 系统性偏低，90% 以上的帧跌破闭眼线。

**缓解措施**：
- 双通道融合 + 语义否决（实测验证有效）
- 数据质量门控排除极端角度

**残留风险**：质量门控目前只限制侧转（38°）与侧倾（28°），
不限制俯仰——因为低头是疲劳信号，不能当坏数据丢弃。
所以若驾驶员在头部大幅后仰的**同时**真的闭眼，两个通道会给出冲突判断，
目前的设计是"宁可漏报也不误报"（语义否决优先）。

**论文建议**：配一张分桶统计图（pitch 分段 vs EAR 均值 vs 语义通道均值），
量化这个不对称性。

### 2. 参数为单被试标定值

**具体**：语义否决阈值 0.40、融合权重、部分滞回带宽度。

**影响**：校准逻辑本身是个性化的（每次启动都记录当前被试的睁眼基线），
但融合层参数是全局的，取值依据来自单人实测，跨人群适用性未验证。

**缓解措施**：
- 提供参数调节界面（专业模式的滑块）
- 敏感性分析工具可验证"稳定平台区"——参数在一定范围内变化时结论稳定

**论文建议**：作为局限性单独说明，并指出这是原型系统的固有限制，
工程化部署前需要多被试标注数据重新标定。

### 3. 准确率未经规模化验证

**现状**：视频评测工具已就绪，可计算混淆矩阵、灵敏度、特异度与响应延迟，
但缺少多被试标注数据集。

**可以说的**：
- 系统在受控条件下可用（真人实测 8 分钟 0 次误报）
- 各功能模块单独测试通过
- 提供了完整的评测工具链

**不能说的**：
- 不能外推为普适准确率
- 不能声称优于现有方法（没有对照实验）

**论文建议**：老实说「准确率验证需要标注数据集，这是后续工作」，
同时强调本系统的贡献在于**工程实现与方法论**——双通道融合、
质量门控、离线评测工具，而不是准确率数字。

### 4. 主观标注的固有噪声

**问题**：视频评测采用被试自评标签（正常 / 疲劳），等价于 KSS 量表的简化。
自评受主观因素影响，不同被试对"疲劳"的理解不一致。

**为什么不做四级标注**：主观自评无法可靠区分轻度与中度，
强行标四级会引入更多噪声。系统内部仍输出四级，但评测只用二分类验证。

**论文建议**：引用相关研究说明主观量表的固有噪声（KSS、SSS），
指出这是该领域的共性问题，不是本系统特有的。

### 5. 浏览器环境的性能限制

**帧率**：MediaPipe Face Landmarker 在笔记本 CPU 上约 10–15 FPS，
开启 GPU 委托可达 20–25 FPS。低于专用硬件（30 FPS 以上）。

**影响**：瞬时动作（如快速眨眼）可能漏采样。缓解措施是用时间加权窗口而不是帧数窗口。

**优势**：零部署成本、隐私保护、跨平台。论文应把这作为设计权衡而非缺陷。

## 评测方法论

### 混淆矩阵与准确率指标

系统提供视频离线评测工具 (`evaluation.js` + `evaluator.js`)，
可计算以下指标：

```
              实际正常    实际疲劳
预测正常        TN         FN
预测疲劳        FP         TP

灵敏度 = TP / (TP + FN)      # 查全率，疲劳时报警的比例
特异度 = TN / (TN + FP)      # 正常时不误报的比例
准确率 = (TP + TN) / 总样本
```

**响应延迟**：从实际进入疲劳到系统报警的时间间隔。

### 视频评测操作流程

详见 [`视频评测指南.md`](视频评测指南.md)。简要步骤：

1. 录制一段视频（包含清醒与疲劳两个阶段）
2. 在评测界面逐段标注：拖动时间轴，点「标为正常」或「标为疲劳」
3. 系统以固定步长（默认 100ms）逐帧推理，输出逐点数据与指标汇总
4. 导出 CSV：`视频评测逐点数据_*.csv`（含每一帧的预测值与标签）、
   `视频评测指标汇总_*.csv`（混淆矩阵与准确率）

**关键设计**：
- 固定步长而非摄像头帧率——保证不同设备上结果可复现
- 标签与预测分开存储——便于事后调整标注或参数重跑

### 敏感性分析与权重消融

**敏感性分析**：把本次会话的指标序列在多组参数下离线重算，
找出"稳定平台区"——参数在某个范围内变化时，结论（等级分布、报警次数）基本不变。
用于回答"为什么阈值取这个值"。

**权重消融**：逐项扣除某指标的贡献（权重置 0），观察分数变化，
量化每个特征的实际作用。

两个工具的输出都是 CSV 表，可直接用于论文插图。
